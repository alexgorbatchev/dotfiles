# pkg/scaffold

Starter tool configuration provisioning, tsconfig scaffolding, and legacy template migration.

## Commands

- Test: `go test ./pkg/scaffold/...`

## Local conventions

- Explicit user operation: starter tool configurations (`dotfiles.tool.ts`, `typescript.tool.ts`, `brew.tool.ts`) are only provisioned via `scaffold.Run` (`dotfiles tool scaffold`). Loading configurations never creates files automatically.
- Non-destructive updates:
  - Existing files matching default templates are reported as `ActionSkipped`.
  - Unedited older versions generated by past dotfiles releases are detected via `legacyContents` and reported as `ActionOutdated` without being overwritten when `opts.Force` is false.
  - When `opts.Force` is true, user-edited files are backed up via `backup.Reserve` before overwriting (`ActionOverwrote` with `BackupPath`); legacy generated files are safely overwritten without backup.
- TypeScript configuration (`ProjectTSConfig`): writes a minimal root `tsconfig.json` that extends the CLI-owned tsconfig under `.generated/` (`{"extends": "..."}`).
- Legacy tsconfig detection (`IsLegacyProjectTSConfig`): detects unedited boilerplate `tsconfig.json` generated by previous versions so it can be replaced cleanly.
- Target platform selection: `brew.tool.ts` is only scaffolded when `TargetOS` is `"darwin"`.

## Local gotchas

- Starter configurations must never be auto-created during normal CLI runs or config loading -> only explicit scaffolding generates them.
- `dotfiles tool scaffold` without `--force` will never overwrite existing or outdated tool files.

## Boundaries

- Always: automatically record all new instructions in the most appropriate `AGENTS.md` file immediately upon receipt (check with user if existing instructions conflict).
- Always: write matching unit tests in `scaffold_test.go` and `scaffold_load_test.go`.
- Ask first: adding new starter templates or modifying legacy template signatures.
- Never: overwrite modified user tool files without creating a `.bak` copy.
