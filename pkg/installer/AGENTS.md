# pkg/installer

Tool installer plugins (github-release, curl-script, cargo, brew, apt, dnf, pacman, pkg, etc.).

## Commands

- Test: `go test ./pkg/installer/...`

## Local conventions

- Support slash-delimited `/pattern/flags` syntax across `compileRegex` and `MatchAssetPattern` for JavaScript `RegExp` interoperability.
- Homebrew installer (`BrewInstaller`): `trust` defaults to `false`. When `trust: true`, automatically trust configured `tap`(s) before tapping/installing.
- Always use the injected `fs.FS` (`ResolvedFS.IsAbs()` / `ResolvedFS.Abs()`) for resolving user/tool paths (such as `binaryPath` in manual installer) instead of raw stdlib `filepath.IsAbs`.
- Resolve a `binaryPath` install parameter only through `ResolveBinaryPath` (`binary_path.go`, v1 `expandToolConfigPath` rules), which `manual`, `curl-script` and the orchestrator share so the same value cannot mean different paths depending on who reads it.
- `curl-script` never searches system directories for a binary its script installed elsewhere. Without `binaryPath` the declared binaries must be in the staging directory; with it, the one declared binary is symlinked to the path as written (never copied, never to the path's resolved target) so self-updating tools stay current.
- Log `INFO` progress messages when fetching API releases, downloading assets, and extracting archives.
- Decide whether a download is an archive with `archive.IsSupported` / `archive.Extension`; never keep a local list of archive suffixes. Release installers (github-release, gitea-release) hand the downloaded asset to `releaseAssetInstaller` in `release_asset.go`, which extracts archives, installs extensionless assets as the binary, and fails on anything else (unextractable archive formats, checksums, packages) instead of chmod-ing them.
- `MatchAssetPattern` globs support minimatch-style brace alternation (`*.{tar.xz,zip}`) via `expandBraces` over `path.Match`, matching the v1 matcher.
- `DmgInstaller` installs the app bundle with `installAppBundle` (`app_bundle.go`): it copies the bundle with `fs.CopyTree` into a hidden sibling of `/Applications/<App>.app`, moves the installed bundle aside, renames the copy into place and only then removes the old one, restoring it if the swap fails; once the new bundle is in place, a failure to remove the old one is a warning, not a failed install, and `Uninstall` removes both hidden siblings with the app. A reinstall therefore replaces the bundle (as v1's `rm -rf` + `cp -R` did) and never leaves the user without the app. `findFileWithExtension` searches an extraction without following symlinks, since an extracted `.dmg` keeps links such as `Applications -> /Applications`, and returns only a regular file or a real directory, never a link that `installer -pkg` or `hdiutil attach` would follow.
- `PromoteBinaries` judges a binary by the file its link chain finally names, resolved component by component through `fs.FS` (`resolveLinks` in `binary_link.go`, never `filepath.EvalSymlinks` or a lexical join), and chmods only a regular file inside the directory it was given; a binary that resolves to anything but a regular file fails under either policy, and each binary is judged again at its promoted path, since a relative link renamed to the root reads its target from another directory. Every caller passes an `OutsideLinkPolicy`: a tree extracted from a download (release assets, `curl-tar`, cargo prebuilt archives) passes `RejectOutsideLinks`, which fails the install naming the link and its target; a directory a tool's own installer populated (`curl-script` staging, `cargo install --root`) passes `KeepOutsideLinks`, which keeps the link, leaves its target's mode alone and fails when that target is not an executable file. All binaries are checked before any is promoted. `fs.FS` has no `Lchmod`, and chmodding the link itself would not make the binary executable.
- Implement installer plugins by satisfying the `Installer` interface in `pkg/installer/installer.go`. The load accepts only the method names in `config.InstallMethods()`, so a new installer's name is also added there and to the `InstallMethod` union in `pkg/vm/dsl-types.ts` (see `pkg/config/AGENTS.md`); `TestRegisteredInstallersMatchConfigInstallMethods` fails until it is.
- Read the version an installation asks for with `tool.RequestedVersion()` (`pkg/config/install_params.go`), never from `tool.InstallParams["version"]` or `tool.Version` directly: `tool update` and the dashboard refuse exactly what it names as a pin, so an installer that read a version elsewhere could be moved off a pin the refusal never sees.
- A `CheckUpdate` that has no way to learn the latest upstream version for the tool it was given returns `ErrUpdateCheckUnsupported`, never an empty `UpdateCheckResult`: callers report the sentinel as "update check not supported" (`tool update <tool>` then reinstalls, as v1 did, while updating everything skips unless `--force`; `tool check` and the dashboard say so), while an empty result reads as "up to date".
- A `CheckUpdate` returns a result only when its query positively answered. A query that fails, prints no version, or cannot be told apart from a failure returns an error naming the command and what it printed (`runQuery` / `queryResult.fail` in `query.go`, which keep stdout, stderr and the exit status apart), or only the deciding line of a full answer, quoted in the cause and passed to `queryResult.refuse`. brew fails a check for a formula or cask with no installed version, since `brew info` calls it not outdated; apt reads only the `apt-cache policy` section headed with the package's own name (bare for a native-architecture qualifier, since apt prints `bash:` for `bash:arm64`), because an unknown name that reads as a regular expression (`perl-bas.`) lists the packages it matches instead; it fails empty output, no such section, `Installed: (none)` or no candidate, all of which exit 0, and runs the query with `LC_ALL=C` because apt translates those labels; pacman `-Qu` is current only on exit 1 with nothing on either stream; dnf confirms the installation with `rpm -q` and then reads `dnf check-update`'s exit status (100 lists an upgrade, 0 none), passing `--setopt=*.skip_if_unavailable=False` because a skipped unreachable repository otherwise still exits 0. github-release and gitea-release reject a missing or malformed `repo` with `validateReleaseRepo`, the same check `Install` runs.
- An installer whose `CheckUpdate` can only describe the package installed on this machine (brew, apt, dnf, pacman) declares the unexported `checksInstalledPackage()` marker, which `UpdateCheckNeedsInstallation` reports; `orchestrator.CheckTool` then never asks it about a tool dotfiles never installed. A new package-manager installer must declare it too (`TestUpdateCheckNeedsInstallation` lists every installer).
- `CargoInstaller.Install` and `CheckUpdate` read the binary and version sources only through `tool.CargoSources()` (`pkg/config/cargo_params.go`), whose configuration errors fail the install or check outright. The compile fallback is only for a well-formed configuration whose version lookup or prebuilt download failed; a configuration error, or a source the installer has no case for (`errUnhandledCargoSource`), never reaches `cargo install`.
- `CargoInstaller.CheckUpdate` resolves the latest version through `resolveVersion`, the same `versionSource` dispatch `Install` uses (crates.io by default), and wraps a failed query as an error naming the tool. Keep one resolution path so a check never reports a version the install would not fetch.
- A cargo crate's latest version is its newest stable release unless the tool sets `prerelease: true`, which `resolveVersion` applies to the crates-io and github-releases sources (cargo-toml reads the one version its file declares): crates.io answers with `max_stable_version` (`max_version` only with `prerelease`) and a crate with no stable release is an error naming it; the `github-releases` source passes `prerelease` to `githubReleaseClient`, so `releaseEndpoint` decides exactly as it does for github-release. Never take crates.io `max_version` or `newest_version` as the default, and treat `max_version` `0.0.0` without a `max_stable_version` as crates.io's placeholder for a crate with no version.
- When a cargo prebuilt download fails, `cargoFallbackVersion` decides what the `cargo install` fallback compiles: the pinned version, else the resolved one when crates.io resolved it (`cargoVersion.published`) or the tool sets `prerelease`, provided it is an exact crate version (`isCrateVersion`, MAJOR.MINOR.PATCH[-pre][+build], the only form `--version` takes without an operator; `semver.Canonical` discards build metadata, so it is not compared on its own, and MAJOR, MINOR and PATCH must fit a u64 as in the semver crate); that version is returned as installed. A Cargo.toml or release-tag version without `prerelease` is never passed, since it need not be published. Otherwise cargo picks its own newest stable release, which a `prerelease` opt-in refuses with an error instead. crates.io answering that a crate has no installable version (`errNoCrateVersion`) fails the install without compiling.
- `installPrebuilt` reports a failure as a `prebuiltFailure` naming the step that failed (`version resolution`, or `<binarySource> download`), and the compile-fallback warning is tagged with the tool and names that step with its cause folded into the message (`%v`), as `pkg/logger/AGENTS.md` requires of a user-facing cause. `Install` reads `prerelease` once (`cargoPrerelease`) and hands the same value to `resolveVersion` and `cargoFallbackVersion`.
- `CargoInstaller.Install` strips a leading `v` from the pin once, right where it reads `tool.RequestedVersion()`, so the prebuilt download, the `cargo install --version` fallback (cargo's `parse_semver_flag` rejects a leading `v`) and the returned `InstallResult.Version` all see the same bare version, and a pin that is still no version after that one strip (`v`, `vv1.2.3`) is an error, in a dry run too, rather than an install of the latest version or a `--version` cargo rejects. Never pass `RequestedVersion()` or `*tool.Version` further down unnormalised.
- A cargo `github-releases` download of a version without a known tag (pinned by `.version()` or by `tool update`) tries each spelling `releaseTagCandidates` returns for the bare version (`v<version>`, then `<version>`) against the download URL itself, never the GitHub API, which is rate limited. Only a 404 (`downloader.StatusError`) moves on to the next spelling; any other failure is returned.
- `CargoInstaller` takes every host, token, cache and the User-Agent from `CargoSettings`, built only by `NewCargoSettings(projCfg)` and applied with `SetCargoSettings` wherever `SetGitHubSettings` is (install pipeline, `configureInstallerForUpdate`, the dashboard's `configureInstallers`, once at server start). Never add per-field URL overrides for tests; point the settings' hosts at an `httptest` server instead. A cargo token is only sent to the host it is configured for (a `cargoTomlUrl` elsewhere goes unauthenticated), and the crates.io/Cargo.toml response caches are keyed by URL alone; a crates.io answer of `errNoCrateVersion` is definitive and cached like a version.
- github-release and gitea-release cache release metadata only through `releaseCache` (`release_cache.go`), keyed by `releaseCacheKey` (API host, repository, version, prerelease for `latest`, SHA-256 of the token). The installers are registered once per process, so the TTL (`CacheTTL`, github-release's from `github.cache.ttl`) bounds the in-memory entries as well as the on-disk ones, and an entry promoted from disk keeps the file's age. Never add a lookup that serves memory without the TTL check or a key without the host and credentials.
- `UvInstaller` installs Python CLI tools into isolated virtual environments using `uv tool install`. It sets `UV_TOOL_BIN_DIR=${stagingDir}` so launcher binaries land directly in dotfiles' staging area, and passes `KeepOutsideLinks` to `PromoteBinaries` because uv populates the staging directory with symlinks pointing into uv's isolated tool virtual environment (`~/.local/share/uv/tools/<package>/bin/`). Forced reinstalls and automated updates (`config.IsForceEnabled(ctx)` or `force: true`) pass `--force` to `uv tool install` so native uv overwrites existing environments without error. Package names fall back to `tool.Name` when empty, and `_` and `.` are normalized to `-` when matching package names in `uv tool list`. `CheckUpdate` queries PyPI JSON API (`https://pypi.org/pypi/<package>/json`) using an HTTP client with a 30s timeout, respecting context deadlines.

## Local gotchas

- Unlogged network requests or asset downloads look like hung processes -> always log explicit progress steps (`Fetching release info...`, `Downloading...`, `Extracting...`).

## Boundaries

- Always: automatically record all new instructions in the most appropriate `AGENTS.md` file immediately upon receipt (check with user if existing instructions conflict)
- Always: write matching unit tests in installer test files for any installer modifications.
- Ask first: adding new installer plugin types or changing installer interface contracts.
- Never: perform silent background downloads without logging progress.
